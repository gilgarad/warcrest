# 전장 지형 렌더링 진단과 점진적 전환 계획

## 결론

현재 이질감은 단순히 "타일맵이 없기 때문"만은 아니다. 핵심 원인은 다음 네
가지가 겹친 것이다.

1. 플레이 영역 전체가 한 장의 저해상도 배경으로 렌더링된다.
2. 논리 지형, 이동 경로, 거점, 장애물 데이터가 하나의 맵 모델로 연결되어
   있지 않다.
3. 배경, 건물, 나무, 유닛이 서로 다른 투시각, 비율, 디테일 밀도, 조명으로
   제작되어 있다.
4. 건물 footprint, 지면 데칼, 접지 그림자, 배경 오브젝트 가림 정보가 없다.

따라서 최종 권장안은 **원경 매트 배경 + 플레이 가능 구간의 타일/데칼 +
논리 지형 그리드 + footprint 기반 오브젝트**를 결합한 하이브리드 구조다.
전체 월드를 한 번에 순수 타일맵으로 바꾸지 않고, 중앙 거점 주변의 최소
프로토타입부터 교체한다.

## 현재 엔진과 렌더링 구조

### 엔진

- Phaser `3.90`
- TypeScript + Vite
- 고정 내부 해상도 `1600 x 900`
- `Phaser.Scale.FIT`으로 브라우저 화면에 맞춤
- 기본 물리 엔진은 Arcade Physics지만, 현재 레인 전투 유닛 이동에는
  물리 body나 tile collision을 사용하지 않는다.

### 배경

- `lane-battlefield-object-base-v4.png` 한 장을 월드 전체 배경으로 사용한다.
- 원본 해상도는 `1692 x 929`다.
- 이를 `7000 x 3900` 월드 크기로 약 4.1배 확대한다.
- 카메라 줌은 `0.46`이므로, 실제 화면에서도 배경 원본 한 픽셀이 약 1.9
  화면 픽셀로 확대되어 보인다.
- 배경 속 원경 절벽, 벽, 폐허, 잔디, 길은 모두 depth `0`의 한 이미지다.
  따라서 배경에 그려진 벽이나 돌은 유닛을 가릴 수 없다.

### 오브젝트

- 본진, 타워, 나무, 바위는 투명 PNG `Image` 오브젝트다.
- 타워 표시 크기는 `148 x 176`, 본진은 `340 x 300`이다.
- 타워와 나무는 origin을 하단 근처에 두고 접지점 `y`로 depth를 계산한다.
- 타워 상태는 건재, 손상, 치명 손상, 폐허, 건설 중 텍스처로 교체한다.
- 건물 footprint나 지면 점유 셀은 없다.

### 유닛

- 유닛 위치는 월드 `x/y`가 아니라 `progress + laneRow`가 원본 데이터다.
- `progressToScreen()`이 다중 노드 레인 경로를 따라 월드 좌표로 변환한다.
- 유닛끼리의 거리와 전투 사거리도 `progress/laneRow` 공간에서 계산한다.
- 원본 유닛 프레임은 약 `444 x 887`의 세로형이지만, 화면에서는
  `76 x 76` 정사각형으로 강제 변형된다.
- 그림자는 별도 타원 Graphics이며 크기, 색, 방향이 거의 고정이다.

### 깊이와 카메라

- 전장 카메라와 UI 카메라는 분리되어 있다.
- 전장 카메라는 드래그 이동하며, 줌은 현재 고정이다.
- 유닛, 타워, 나무는 `180 + groundY * 0.1` 공통 depth 공식을 사용한다.
- 이 공식은 동적 오브젝트끼리의 앞뒤 순서에는 유효하다.
- 한 장의 배경 내부 요소에는 depth 정보가 없으므로, 배경 벽/바위/절벽과
  동적 유닛 사이의 가림은 해결하지 못한다.

### 논리 전장 데이터

- `battlefieldGenerator.ts`에는 `40 x 22` 타일 크기, 3칸 폭 레인, 본진,
  거점 좌표가 이미 정의되어 있다.
- 그러나 현재 화면 렌더링, 유닛 이동, 거점 배치에는 이 타일 데이터가
  사용되지 않는다.
- 화면은 `LaneBattleScene` 안의 별도 `lanePath`, 하드코딩된 거점 progress,
  수동 장애물 배열을 사용한다.
- `battlefieldGenerator` 결과는 현재 주로 `window.__gameDebug` 출력에만
  남아 있다.

## 스크린샷 원인 분석

| 항목 | 현재 문제 | 영향 |
|---|---|---|
| 배경 표현 | 플레이 월드 전체가 한 장의 그림 | 지면 재질, 높이, 가림, 충돌 정보를 분리할 수 없음 |
| 원근/카메라 | 배경은 높은 사선 시점, 유닛은 측면 인물화, 타워는 낮은 3/4 시점 | 같은 공간을 공유하지 않는 콜라주처럼 보임 |
| 스케일 | 배경은 회화적 원근을 포함하지만 동적 오브젝트는 위치와 무관한 고정 크기 | 화면 위쪽과 아래쪽의 공간감이 일치하지 않음 |
| 해상도 | `1692 x 929` 배경을 `7000 x 3900`으로 확대 | 배경은 흐리고 오브젝트 외곽은 상대적으로 선명함 |
| 디테일 밀도 | 배경 유닛 규모의 작은 세부와 고해상도 타워/나무가 혼합 | 자산마다 축척과 화풍이 다르게 읽힘 |
| 색감/조명 | 배경은 저채도 올리브색, 오브젝트는 강한 금색/청색/검은 명암 | 오브젝트가 배경에서 튀어나와 보임 |
| 접지 그림자 | 유닛은 고정 타원, 건물/나무는 런타임 그림자 없음 | 지면 방향광과 오브젝트 무게감이 연결되지 않음 |
| 지형 연결 | 건물 하부에 기초, 흙 눌림, 잔디 제거, 도로 손상 데칼이 없음 | 건물이 지면 위에 붙인 스티커처럼 보임 |
| 렌더링 순서 | 동적 오브젝트끼리는 개선됐지만 배경 내부 구조물은 항상 맨 뒤 | 유닛이 배경 벽과 바위를 관통해 보임 |
| 요새 결합 | 배경 원형 패드 + 선택 ring/core + 타워가 별도 요소 | 하나의 요새보다 "표식 위에 놓인 타워"로 읽힘 |
| 유닛 비율 | 세로형 원본 프레임을 정사각형으로 강제 표시 | 캐릭터 체형과 동작 실루엣이 눌리고 부자연스러움 |

## 타일맵 필요성 판단

### 필요한 것

플레이 가능 영역에는 타일 또는 타일과 동등한 **구조화된 지형 데이터**가
필요하다.

- 잔디, 흙, 도로, 석재와 전이 경계
- walkable / blocked / buildable 정보
- 건물 footprint와 거점 socket
- 나무, 바위, 벽의 점유와 occluder 정보
- 레인 경로와 시각적 도로의 일치

### 반드시 필요하지 않은 것

월드 전체를 작은 반복 타일로 채울 필요는 없다.

- 전투와 건설이 일어나지 않는 원경 절벽, 강, 숲은 큰 매트 이미지나 청크로
  유지해도 된다.
- 순수 타일만으로 현재의 회화적 배경 품질을 재현하면 타일 반복과 높은
  아트 제작비가 새 문제가 된다.

즉, **논리 지형 그리드는 필요하지만 전체 순수 타일 렌더러는 아직 최선이
아니다.**

## 대안 비교

| 방식 | 장점 | 단점/위험 | 범위 | 현재 호환성 |
|---|---|---|---|---|
| A. 전체 타일맵 | 충돌/건설/지형 경계가 명확하고 맵 확장이 쉬움 | 완성도 높은 전이 타일셋 제작량이 크고 반복감 위험 | 큼 | 중간 |
| B. 배경+타일/데칼 하이브리드 | 원경 품질을 보존하며 플레이 구간만 구조화 가능 | 배경과 타일 경계의 색/해상도 연결 작업 필요 | 중간 | 높음 |
| C. 청크 지형 | 큰 맵, 다인전, culling과 스트리밍에 유리 | 청크 제작/이음새/도구화가 복잡하고 현재 1레인에는 과함 | 큼 | 중간 |
| D. 배경 유지+주변만 보정 | 가장 빠르고 기존 기능 영향이 작음 | 배경 가림과 논리 지형 불일치는 남으므로 최종 해결책이 아님 | 작음 | 매우 높음 |
| E. 논리 그리드+레이어 렌더러 | 시뮬레이션과 시각을 통합하면서 렌더 방식은 단계적으로 교체 가능 | 초기 데이터 모델과 좌표 변환 설계가 필요 | 중간 | 높음 |

권장안은 **E를 기반으로 B를 구현**하고, 맵이 커지는 시점에 C의 청크 렌더링을
추가하는 것이다. D는 첫 검증용 폴리싱에만 사용한다.

## 추천 최종 구조

```text
BattlefieldMapSpec
  ├─ terrain grid: grass / dirt / road / stone / height
  ├─ flags: walkable / buildable / blocked
  ├─ lane graph: base -> capture nodes -> base
  ├─ structure sockets: footprint / anchor / owner
  └─ prop placements: trees / rocks / walls / occluders

BattlefieldRenderer
  ├─ far matte or large background chunks
  ├─ playable terrain base tiles
  ├─ transition tiles and decals
  ├─ footprint and contact-shadow layer
  ├─ props and structures
  ├─ units and projectiles
  └─ selection/VFX/UI layers

Existing lane simulation
  progress + laneRow
      -> LanePathAdapter
      -> world x/y on BattlefieldMapSpec
```

기존 전투는 당장 grid pathfinding으로 교체하지 않는다. `progress/laneRow`
시뮬레이션을 유지하고 `LanePathAdapter`가 새 맵 데이터의 lane graph를
월드 좌표로 변환하게 한다. 이후 다중 레인이나 자유 이동이 필요할 때
flow field 또는 grid pathfinding으로 확장한다.

## 수정 대상

### 기존 파일

- `src/scenes/LaneBattleScene.ts`
  - preload, 배경 그리기, 하드코딩 경로/거점, 오브젝트 생성, depth와 shadow
    코드를 단계적으로 분리한다.
- `src/systems/battlefieldGenerator.ts`
  - 현재 사용되지 않는 타일 데이터를 실제 맵 규격의 원본으로 승격한다.
- `src/main.ts`
  - 필요할 경우 렌더러의 antialias, roundPixels, texture filter 정책만 조정한다.
- `src/data/unitRosters.ts`
  - 전투 구성은 변경하지 않는다. 자산 메타데이터 연결만 별도 레지스트리로
    이동할 수 있다.

### 새 모듈 후보

- `src/data/battlefieldMaps.ts`
  - terrain, lane graph, sockets, props를 가진 맵 정의
- `src/gfx/battlefieldRenderer.ts`
  - 타일/전이/데칼/원경/오브젝트 레이어 생성
- `src/gfx/spritePresentation.ts`
  - 원본 비율, ground anchor, 표시 높이, shadow, color grade 메타데이터
- `src/systems/terrainGrid.ts`
  - walkable/buildable/blocked 질의
- `src/systems/structureFootprints.ts`
  - 건물 점유, 건설 socket, 폐허/건설 중 상태

### 새 자산 후보

- 잔디, 흙, 도로, 석재 기본 타일
- 재질별 모서리/코너/전이 타일
- 바퀴 자국, 균열, 잡초, 흙먼지 데칼
- 타워/본진/거점별 foundation 및 rubble 데칼
- 방향이 통일된 접지 AO와 그림자 자산
- 공통 카메라 각도와 팔레트로 다시 맞춘 유닛/건물/장식 자산

## 단계별 구현 계획

### 0단계: 기준선 고정

- 현재 빌드의 시작, 중앙 교전, 거점 점령 상태를 스크린샷과 debug JSON으로
  고정한다.
- 카메라 줌, 월드 크기, lane progress, 거점 상태를 회귀 기준으로 저장한다.

완료 기준:

- 같은 시간대의 전투 상태를 전환 전후 비교할 수 있다.
- 시각 변경이 경제/웨이브/전투 수치에 영향을 주지 않았음을 확인할 수 있다.

### 1단계: 중앙 거점 최소 프로토타입

- 중앙 거점 주변 약 `8 x 8` 논리 셀만 새 방식으로 렌더링한다.
- 잔디, 흙, 석재 도로 3재질과 최소 전이 타일을 사용한다.
- 중앙 타워에 foundation decal, 접지 AO, 방향성 그림자를 적용한다.
- 유닛 원본 종횡비와 ground anchor 메타데이터를 적용한다.
- 기존 배경과 경로/전투 로직은 유지한다.
- 기능 플래그로 기존/프로토타입 렌더링을 즉시 비교할 수 있게 한다.

완료 기준:

- 기본 줌에서 타일 반복과 외곽 seam이 먼저 눈에 띄지 않는다.
- 타워가 원형 패드에 붙인 이미지가 아니라 지면에 세운 구조물처럼 보인다.
- 유닛 발과 그림자가 도로 표면에 맞고, 원본 체형이 찌그러지지 않는다.
- 전투, 점령, 건설, 타워 공격 결과가 기존 debug 값과 같다.

### 2단계: 맵 데이터 통합

- 하드코딩된 `lanePath`, 거점 progress, 장애물 배열을 `BattlefieldMapSpec`으로
  이동한다.
- `battlefieldGenerator`와 화면 전장을 하나의 원본 데이터로 통합한다.
- 기존 `progress/laneRow` API는 adapter로 유지한다.

완료 기준:

- `LaneBattleScene`에 본진/거점 월드 좌표가 하드코딩되어 있지 않다.
- debug capture point와 화면 capture point가 같은 데이터에서 나온다.
- 이전과 같은 웨이브 진행과 전투 타이밍이 유지된다.

### 3단계: 플레이 가능 레인 스트립 전환

- 본진 사이의 도로와 도로 양옆 전투 가능 영역만 타일/전이/데칼로 교체한다.
- 멀리 떨어진 산, 강, 숲, 성벽은 기존 원경 배경 또는 큰 청크로 유지한다.
- lane glow는 디버그/선택 상태 외에는 제거하거나 약화한다.

완료 기준:

- 전장 전체를 드래그해도 길과 잔디 경계가 끊기지 않는다.
- 전투 가능한 영역의 모든 표면이 논리 terrain cell과 일치한다.
- 같은 패턴이 연속으로 반복되는 느낌이 데칼 변형으로 완화된다.

### 4단계: footprint와 오브젝트 결합

- 타워, 본진, 나무, 바위, 벽에 footprint와 occluder를 정의한다.
- 건설 전, 건설 중, 완성, 손상, 폐허 상태마다 지면 데칼을 연결한다.
- 큰 구조물은 필요하면 base/top 레이어로 분리해 가림을 안정화한다.

완료 기준:

- 유닛이 구조물 footprint를 관통하지 않는다.
- 구조물 뒤의 유닛은 가려지고 앞의 유닛은 정상적으로 보인다.
- 구조물이 사라져도 foundation/rubble 상태가 지면에 남는다.

### 5단계: 이동과 시각 지형 일치

- 장애물 회피를 수동 `laneRow` 밀어내기에서 terrain/footprint 질의로 바꾼다.
- 기존 lane 진행은 유지하되, 각 row가 실제 도로 폭 안에 있는지 검증한다.
- 향후 다중 레인용 lane graph와 flow field 확장 지점을 둔다.

완료 기준:

- 유닛이 화면에 보이는 벽, 바위, 나무, 건물을 통과하지 않는다.
- 길이 휘어지는 구간에서도 대열이 도로 밖으로 벗어나지 않는다.
- 후열 합류와 전투 슬롯 로직이 새 지형 질의 후에도 유지된다.

### 6단계: 아트 통합

- 공통 카메라 각도, 광원 방향, 팔레트, 명암 대비, edge softness 규칙을
  고정한다.
- 유닛, 건물, 장식 자산을 같은 규칙으로 재생성하거나 보정한다.
- 월드 전체에 약한 공통 color grade와 거리별 대비 규칙을 적용한다.

완료 기준:

- 배경과 오브젝트의 선명도와 채도 차이가 의도된 범위에 있다.
- 타워, 나무, 유닛이 같은 방향의 빛과 그림자를 가진다.
- 시작, 중앙, 적 본진 화면 모두에서 "붙인 이미지" 인상이 현저히 줄어든다.

### 7단계: 성능과 확장

- 맵이 커지거나 다인전 레인이 늘면 terrain layer를 청크/RenderTexture로
  캐시한다.
- 화면 밖 props, effects, labels를 culling한다.

완료 기준:

- 현재 최대 웨이브 밀도에서 목표 프레임을 유지한다.
- 2~4인용 lane graph를 추가해도 렌더 구조를 다시 갈아엎지 않는다.

## 기존 기능 위험

- 좌표 변환 오차로 타워 사거리, 점령 반경, 투사체 목표점이 달라질 수 있다.
- 유닛 종횡비와 anchor 수정 시 HP바, 이름표, 공격 이펙트 위치가 어긋날 수 있다.
- footprint 충돌을 바로 강제하면 기존 병력 대열이 막히거나 후열 정체가
  재발할 수 있다.
- 시각 타일 좌표와 기존 progress 좌표를 동시에 관리하면 두 원본이 생길 수
  있다. `BattlefieldMapSpec`을 유일 원본으로 만들어야 한다.
- 배경과 타일 경계의 색/해상도 seam이 새 이질감이 될 수 있다.
- 많은 고해상도 타일과 상태별 건물 자산은 texture memory를 늘린다.
- 매 프레임 모든 오브젝트 depth 정렬과 terrain query를 수행하면 유닛 수가
  늘 때 성능 저하가 생길 수 있다.
- 선택 ring, 클릭 hit area, UI 카메라 ignore 목록이 새 오브젝트 계층에서
  누락될 수 있다.

## 첫 최소 검증 프로토타입

범위는 **중앙 거점 한 곳과 주변 `8 x 8` 셀**로 제한한다.

- 기존 배경은 그대로 둔다.
- 그 위에 잔디/흙/석재/전이 타일로 작은 테스트 패치를 만든다.
- 중앙 타워 한 개에 foundation decal과 그림자를 적용한다.
- 투석병, 도끼병, 보급병 각 1기의 원본 비율과 발 anchor를 보정한다.
- 기존 거점 progress, 전투, 점령, 타워 HP 로직은 건드리지 않는다.
- 기존 렌더와 새 렌더를 한 설정값으로 전환해 같은 장면을 비교한다.

이 프로토타입이 성공해야 전체 레인 스트립 전환으로 간다. 실패하면 전체
타일맵 작업을 시작하지 않고, 카메라 각도와 자산 제작 규칙부터 다시 맞춘다.

## 사용자 결정이 필요한 사항

1. 최종 카메라를 2D 고정 사선 시점으로 확정할지, 위쪽으로 갈수록 오브젝트가
   약간 작아지는 의사 원근을 넣을지
2. 원경 매트 배경을 최종 버전에도 유지할지, 장기적으로 전부 청크 지형으로
   바꿀지
3. 지형 아트를 현재의 회화적 반실사 톤으로 유지할지, 워크래프트 계열처럼
   형태와 색 구분이 더 강한 스타일로 조정할지
4. 첫 프로토타입에서 Tiled JSON을 도입할지, TypeScript 맵 데이터로 먼저
   검증할지
5. 타워와 본진 주변을 완전한 충돌 영역으로 만들지, 병력이 둘레를 자연스럽게
   통과하도록 좁은 우회 통로를 둘지

권장 기본안:

- 고정 사선 시점
- 원경 매트 유지
- 현재 반실사 톤을 유지하되 형태/재질 경계는 더 명확하게 조정
- 첫 프로토타입은 TypeScript 맵 데이터
- 건물 footprint 주변에 명시적인 우회 슬롯 제공
