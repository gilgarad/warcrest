# 온라인 1v1 PvP 아키텍처 검토

Issue #7 / 브랜치 `issue-7-pvp-sim-render-split`.
이 문서는 **결정을 받기 위한 검토 자료**다. 구현은 아직 시작하지 않았다.

## 1. 현재 준비도 (실측)

| 항목 | 값 |
|---|---|
| `LaneBattleScene.ts` | 5178줄 / 메서드 150개 |
| 그중 **표현 참조가 전혀 없는 순수 시뮬** | 85개 메서드 · **951줄** |
| 명백한 표현/UI | 47개 메서드 · 1786줄 |
| 시뮬·표현 혼재 | 18개 메서드 · 1222줄 |
| Phaser를 import하는 모듈 | 69개 중 **15개** |
| 그중 시뮬 계층 | `LaneBattleScene.ts`, `lane-combat/projectileLauncher.ts` **2개뿐** |
| 전투 로직의 `sprite.x/y` 직접 참조 | 47곳 |

혼재 1222줄 중 실제로 얽힌 게임플레이는 훨씬 적다:
`setupTerrainPrototypeControls` 580줄(디버그 컨트롤)과
`createUiIconTextures` 202줄(아이콘 생성)은 이름만 혼재이고,
카메라/드래그/이름표 관련 85줄도 순수 표현이다.
**진짜로 손봐야 하는 얽힌 게임플레이 코드는 약 335줄**
(`tickWatchtower`, `tickCapturePoints`, `tickSupport`,
`resolveCapturedStructure`, `applySupportHeal`, `update`).

`src/systems/**`와 `src/data/**`는 **이미 Phaser 무의존**이다. 출발점이 좋다.

### 결정론 위험 요소 (전수 조사)

- **시드 없는 RNG 2곳**: `rollKillResourceReward()`의
  `Phaser.Utils.Array.GetRandom()`이 내부적으로 `Math.random()`이라
  `Phaser.Math.RND.sow([seed])` 시드를 타지 않는다.
  (오디오의 `Math.random()` 3곳은 시뮬에 영향 없음 — 무시 가능.)
- **초월함수**: 시뮬 경로에는 `Math.sqrt`뿐이다. sqrt는 IEEE-754에서
  정확히 반올림되도록 규정되어 엔진 간 결과가 같다. `Math.sin`/`Math.exp`는
  전부 표현 계층(`syncUnitVisual`의 보간, bob 모션)에만 있다.
- **`Math.pow` 1곳**: `frameLerpAlpha()`가 시뮬(레인 조향)에서 쓴다.
  `pow`는 엔진 간 비트 동일성이 보장되지 않는다.
  다만 **고정 타임스텝을 도입하면 `frames = 1`이 되어 `pow`가 사라진다**
  (`1 - (1-a)^1 = a`). 즉 이 위험은 고정 타임스텝으로 자동 해소된다.
- **가변 타임스텝**: 현재 `update(_time, deltaMs)`의 실시간 delta를 그대로
  쓴다. 락스텝이든 서버 권위형이든 고정 타임스텝이 필요하다.

## 2. 이 게임의 결정적 특성

**플레이어는 유닛을 직접 조종하지 않는다.** 입력은 전부 이산적인 경제/건설
명령이고, 그 종류도 7개뿐이다:

`hireWorker` · `shiftWorker` · `tryBuildAtSelectedPoint` ·
`tryDismantleSelectedPoint` · `tryRebuildSelectedDefenseTower` ·
`advanceAge` · `applyPlayerResearchDraft` (+ 즉시 웨이브)

빈도는 분당 수 회 수준이다. 유닛 300기의 거동은 전부 자율이다.

이게 네트워크 방식 선택을 사실상 결정한다:

| 방식 | 대략적 대역폭 |
|---|---|
| 상태 스냅샷 동기화 | 유닛 300 x 약 20B x 10Hz ≈ **60 KB/s** |
| 명령만 교환(락스텝) | 분당 10명령 x 약 30B ≈ **5 B/s** |

## 3. 방안 비교

### A. 결정론적 락스텝 + 얇은 릴레이 서버 (추천)

양쪽 클라이언트가 **동일한 시뮬을 각자 돌리고**, 주고받는 것은 "몇 번째
tick에 무슨 명령"뿐. 서버는 중계·매치메이킹·tick 배리어만 담당한다.

- 장점: 대역폭이 사실상 0. 서버가 게임 로직을 모르므로 아주 작게 유지된다
  (Cloudflare Workers + Durable Objects 무료 티어, 또는 소형 Node WS).
  현재의 GitHub Pages 정적 배포를 그대로 두고 릴레이만 추가하면 된다.
- 단점: **엄격한 결정론이 전제**다. 한 번 어긋나면 그 판은 끝.
  주기적 상태 해시 비교로 desync를 감지해야 한다.
  클라이언트가 전체 상태를 알므로 치팅 여지가 있으나, 이 게임은 원래
  전장 전체가 양쪽에 다 보이므로 정보 우위 문제는 없다.

### B. 서버 권위형 (서버가 시뮬 실행)

- 장점: 클라이언트 간 결정론이 필요 없다(시뮬이 하나뿐). 치팅에 강하고
  관전·재접속이 쉽다.
- 단점: 상시 가동 서버 비용, 300유닛 스냅샷 대역폭, 그리고 **헤드리스 시뮬은
  어차피 필요**하다(같은 리팩터).

### C. P2P 호스트 권위형 (WebRTC)

- 장점: 게임 서버 비용 없음(시그널링만).
- 단점: 호스트 지연 우위, 호스트 치팅 가능, NAT 통과에 STUN/TURN 필요,
  호스트가 나가면 판이 끝난다.

### 중요한 공통점

**세 방안 모두 "헤드리스 결정론 시뮬 분리"가 선행 조건이다.**
따라서 최종 방식을 지금 확정하지 않아도 1단계는 바로 시작할 수 있고,
1단계를 마친 시점에 더 나은 정보로 결정할 수 있다.

## 4. 제안 단계

1. **헤드리스 시뮬 분리** — 순수 데이터 월드 상태, 고정 타임스텝(30Hz 제안),
   주입식 시드 RNG, Phaser import 0.
   씬은 시뮬 상태를 읽어 그리기만 한다.
   검증: 같은 시드 + 같은 명령 → **Node와 브라우저에서 상태 해시 일치**.
   (덤: 고정 타임스텝은 지난 PR에서 고쳤던 "프레임 의존 lerp" 버그 유형을
   구조적으로 불가능하게 만든다.)
2. **명령 계층** — 위 7개 액션을 tick이 찍힌 직렬화 가능 명령으로 바꾼다.
   싱글플레이도 이 경로를 타게 해서(플레이어 1명짜리 락스텝) 상시 검증된다.
3. **릴레이 + 매치메이킹** — WebSocket 릴레이, tick 배리어,
   입력 지연 2~3 tick, 주기적 해시 비교.
4. **네트코드 폴리싱** — 재접속, desync 복구(스냅샷 리싱크), 지연 은폐.

## 5. 착수 전 정리해야 할 것

- 결정론 누수 2곳(`GetRandom`) 제거 — 시드 RNG로 교체.
- `AiController`도 시뮬 계층이므로 함께 결정론화(연습 모드용으로 유지).
- CI에 **Node vs 브라우저 상태 해시 대조** 테스트를 1단계에서 바로 추가.
  결정론은 나중에 검증하면 이미 늦는다.
